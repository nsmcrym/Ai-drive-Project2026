# TODO機能 V1 要件定義書

## 1. 目的と対象範囲

既存の Express＋TypeScript＋EJS サイトに、授業の受講者がブラウザでTODOを一覧表示、登録、完了切替、削除できる機能を追加する。既存の `/` と `/api/db-check` を維持し、`/todo` の画面から Fetch API で `/api/v1/todos` を操作する。

V1の対象は画面、4つのREST API操作、`todo_tasks` テーブル、環境別テスト記録とする。認証、優先度、絞り込み、タイトル更新は対象外とする。

各学生が用意した Neon PostgreSQL に、既存のDB接続と `DATABASE_URL` で接続する。Vercel PreviewとProductionは同じNeon DBを参照する。認証のない公開URLでは第三者も操作できるため、架空の授業用データだけを使う。`.env` と接続文字列はGitに追加せず、AIにも共有しない。

既存コードの実際の配置は要確認とし、設計書で決める。Fetch処理の `TodoApi` クラスへの分割やメソッド名も設計書で扱う。

## 2. 機能と受け入れ条件

### REQ-01 一覧取得

**操作・入力**　`/todo` を開くと `GET /api/v1/todos` を呼び出す。入力項目はない。

**結果・エラー**　成功時は `200` でID昇順のTODO配列を `data` に返す。0件のときは `data` が空配列となる。サーバー側のエラーは共通仕様に従う。

**受け入れ条件・確認方法**　APIと画面で複数件がID昇順に並ぶことを確認する。初回の空DBまたは講師指定の隔離環境で、`200`、`data: []`、画面の「TODOがありません」を確認する。

### REQ-02 登録

**操作・入力**　画面のタイトル欄に入力して追加ボタンを押す。`POST /api/v1/todos` に文字列の `title` をJSONで渡す。

**結果・エラー**　前後の空白を除いて保存し、`isCompleted` は `false` で開始する。成功時は `201` で採番済みのTODOを `data` に返す。JSON構文エラー、項目欠落、型違いは `400`、空白除去後に0文字または101文字以上なら `422` とする。

**受け入れ条件・確認方法**　前後に空白を含むタイトルを登録し、応答と再取得した一覧で空白が除かれていること、未完了で表示されることを確認する。APIで1文字、100文字、空白のみ、101文字、項目欠落、型違い、壊れたJSONを試し、応答を確認する。

### REQ-03 完了状態の部分更新

**操作・入力**　画面のチェックボックスを切り替える。`PATCH /api/v1/todos/:id` に1以上の整数IDを指定し、JSON本文に真偽値の `isCompleted` を渡す。

**結果・エラー**　対象の完了状態だけを更新し、`200` で更新後のTODOを `data` に返す。ID不正、空本文、項目欠落、型違いは `400`、有効なIDに対応するTODOがなければ `404` とする。

**受け入れ条件・確認方法**　登録時に得たIDを使い、完了と未完了の両方向を試す。再取得して対象の完了状態だけが変わることを確認する。APIで不正なID、空本文、真偽値以外、有効だが存在しないIDを試す。

### REQ-04 削除

**操作・入力**　対象の削除ボタンを押す。`DELETE /api/v1/todos/:id` に1以上の整数IDを指定する。

**結果・エラー**　成功時は `204` で本文なしとする。ID不正は `400`、有効なIDに対応するTODOがなければ `404` とする。

**受け入れ条件・確認方法**　登録時に得たIDを削除し、`204` の空本文と再取得した一覧から対象行が消えることを確認する。不正なIDで `400`、同じIDを再度削除して `404` を確認する。

### 画面の共通動作

`/todo` はEJSで表示し、最大100文字のタイトル入力欄、追加ボタン、各TODOの完了チェックボックスと削除ボタンを備える。0件、処理中、入力エラー、通信エラーを表示する。登録・更新・削除の成功後はFetchで一覧を再取得し、タイトルを安全に表示する。APIエラーは `code` と `message` を使って画面に知らせ、`204` の本文は読み取らない。

## 3. 共通のデータとエラー条件

DBテーブルは `todo_tasks` とする。列は `id`（INTEGER、自動採番・主キー）、`title`（TEXT、必須）、`is_completed`（BOOLEAN、必須、初期値 `false`）、`created_at`（TIMESTAMPTZ、必須、初期値 `NOW()`）。タイトルはアプリ側で前後の空白を除き、1〜100文字であることを確認して保存する。テーブル作成SQLの保存先は `sql/todo/020_create_todo_tasks.sql` とする。

APIのTODOは `{id, title, isCompleted, createdAt}` とする。DBの `is_completed` と `created_at` はそれぞれ `isCompleted` と `createdAt` に変換し、`createdAt` は日時文字列で返す。

GET・POST・PATCHは `{"status":"success","data":...}` を返す。GETの `data` は配列、POST・PATCHでは対象のTODOとする。DELETEの `204` に本文は付けない。

エラー本文は `{"status":"error","code":"...","message":"...","details":[]}` の形式で統一する。SQL文、DB接続文字列、内部エラーの詳細は応答に含めず、DBやSQLの詳細はサーバーのログで確認する。

| HTTP | code | 条件 |
| --- | --- | --- |
| 400 | `BAD_REQUEST` | JSONの構文エラー、必須項目の欠落、型違い、1以上の整数ではないID、PATCHの空本文 |
| 422 | `VALIDATION_ERROR` | 空白除去後のタイトルが0文字または101文字以上 |
| 404 | `NOT_FOUND` | 有効なIDに対応するTODOが存在しない |
| 500 | `INTERNAL_ERROR` | サーバー内部エラーやSQL実行エラー |
| 503 | `DB_UNAVAILABLE` | DB接続が利用できない |

## 4. 環境別確認

ローカル、Vercel Preview、Vercel Productionの各環境で、4操作の正常系、入力エラー、存在しないID、画面操作、既存の `/` と `/api/db-check` を確認する。ProductionはPRマージ後に確認する。環境ごとのURL・日時・結果は `docs/todo/04_test_results.md` に記録し、設計書とテスト結果ではREQ-01〜REQ-04を参照する。

PreviewとProductionが共有するDBに既存データがある場合、0件テストのために既存行を削除しない。0件テストを実施できない場合は理由を記録する。架空の一意なタイトルで登録し、応答で得た自分のIDだけを更新・削除する。
